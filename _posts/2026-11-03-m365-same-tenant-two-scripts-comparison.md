# M365·Azure 실습기 - 같은 테넌트에서 두 스크립트를 돌려 보니 숫자가 달랐다

## 이 글을 한 줄로

> **두 스크립트의 결과가 다를 때, 같은 테넌트에서 둘 다 돌려 보면 "환경 차이"와 "스크립트 결함"이 바로 갈린다.**

---

## 지난번 이야기 (짧게)

[지난 글]({% post_url 2026-10-30-m365-cross-verification-running-others-scripts %})에서는 같은 세트 안의 다른 조 스크립트를 내 Sandbox에서 돌려 봤다.

이번에는 범위가 넓어졌다. 82개 점검 항목을 따로 검증한 **다른 세트의 통합 스크립트**를 받아서 돌리고, 우리 세트 통합본과 82행을 맞춰 봤다. 오후에는 우리 세트의 새 통합 스크립트도 같은 Sandbox에서 돌렸다.

> 모든 실습은 개인 연습용 환경(M365 개발자 Sandbox)에서 **조회만** 했다. 테넌트 이름과 계정은 글에 적지 않았다.

---

## 1. Cloud Shell에서 실행해 달라는 요청 — 로그인부터 막혔다

받은 스크립트는 "Azure Cloud Shell에서 정상 구동되는지 확인해 달라"는 요청과 함께 왔다. 실행하자 이렇게 나왔다.

```
To sign in, use a web browser to open the page https://login.microsoft.com/device and enter the code ...
```

코드를 넣으니 브라우저에 **"이에 대한 액세스 권한이 없습니다"**가 떴다.

- Cloud Shell 안에는 브라우저 창이 없어서, Microsoft Graph 로그인이 처음부터 **디바이스 코드** 방식으로 간다.
- 내 Sandbox는 보안 기본값 때문에 디바이스 코드 로그인이 막혀 있다(지난 글에서도 만난 화면).
- 그래서 이 테넌트에서는 **Cloud Shell로 Graph에 아예 연결할 수 없다.**

> **알게 된 것:** "Cloud Shell에서 된다"는 테넌트 설정에 따라 참이 아닐 수 있다. 결과 보고에는 "디바이스 코드 허용 테넌트에서만 가능"처럼 **조건을 함께** 적어야 한다.

결국 내 PC의 PowerShell 7에서 브라우저 로그인으로 실행했다.

---

## 2. 82행 비교 — 차이를 세 갈래로 나눴다

다른 세트 스크립트 결과를 우리 세트 통합본과 비교했다.

| 구분 | 건수 |
|---|---|
| 같은 결과(같음 + 테넌트 차이 + 표기만 다름) | 40 |
| 상대 스크립트 판정이 비어 있음 | 14 |
| 판독이 다름 | 14 |
| 같은 테넌트에서 값이 다름 | 5 |
| 실행 오류·측정 대상 다름 | 9 |

다른 점은 크게 세 갈래였다.

1. **스크립트 결함** — 값 자체가 틀림
2. **판독 기준 해석** — 같은 값을 다르게 판정
3. **실행 환경** — 어디서, 어떤 순서로 돌렸느냐

---

## 3. 같은 테넌트, 같은 날, 다른 숫자

오후에 우리 세트의 새 통합 스크립트를 **같은 Sandbox**에서 돌렸다. 테넌트가 같으니 차이가 나면 환경 탓이 아니다.

| 항목 | 상대 세트 스크립트 | 우리 통합 스크립트 |
|---|---|---|
| 조치 기한 임박 Message center 게시물 | 6건 | 23건 (전체 458건 조회) |
| 미해결 서비스 이슈 | 0건 | 12건 |
| 구독 Owner | 0명 | 2명 |
| 지정한 비상 계정 | 조회 실패 | 1개 찾음 |

첫 줄은 지난 글과 똑같은 원인이었다. 조회 주소에 `$top=200`을 붙이면 이 API는 **다음 페이지 주소를 주지 않는다.** 그래서 앞쪽 200건만 셌다. 이번까지 세 조의 스크립트에서 같은 실수가 나왔다.

나머지 세 줄은 원인을 아직 모른다. 다만 상대 스크립트의 상세 출력이 비어 있었다. **오류를 잡아서 숨기면 "0"으로 보인다**는 점은 짐작할 수 있다.

> **알게 된 것:** 결과가 다를 때 "환경이 달라서겠지"로 넘어가기 쉽다. **같은 테넌트에서 두 스크립트를 다 돌려 보면** 그 핑계가 사라지고, 결함만 남는다.

---

## 4. 0이라고 다 정상은 아니다 — 우리 스크립트도 마찬가지

상대 스크립트는 이런 경우를 "정상"으로 판정했다.

- 디렉터리 동기화를 **쓰지 않는** 테넌트에서 "동기화 오류 0건"
- Azure Policy가 평가한 리소스가 **하나도 없는데** "비준수 0개"

오류가 없는 게 아니라 **잴 대상이 없는** 것이다. 우리 세트는 이걸 "측정 불가"로 보기로 정해 두었다.

그런데 오후에 돌린 **우리 통합 스크립트도 같은 두 항목을 "정상"으로 냈다.** 지난주 수정본에서는 "측정 불가"였는데 다시 돌아가 있었다.

> **알게 된 것:** 남의 결과에서 찾은 문제는 **내 결과에서도 찾아봐야** 한다. 판정 원칙은 문서에만 있으면 안 되고 스크립트 코드에 들어가 있어야 지켜진다.

---

## 5. 실행 환경이 결과를 바꾼다

PC에서 상대 스크립트를 돌렸을 때 Exchange 관련 3개 항목이 오류였다.

```
Could not load file or assembly '...ExchangeOnlineManagement\3.10.1\netCore\Microsoft.Identity.Client.dll'
```

같은 PowerShell 창에서 **Graph 모듈을 먼저 불러온 뒤 Exchange 모듈을 불러오면**, 두 모듈이 쓰는 로그인 라이브러리(MSAL) 버전이 부딪친다.

우리 세트의 새 통합 스크립트는 이 문제를 피하려고 **서비스별로 PowerShell 창을 나눠서** 차례로 실행한다(Graph·Exchange·Teams → Purview → Azure → SharePoint). 같은 PC에서 82행이 오류 없이 나왔다.

---

## 6. 조회만 한다는 약속

상대 스크립트의 두 항목은 SharePoint 보고서를 **새로 만들기 시작하는** 명령(`Start-SPODataAccessGovernanceInsight`)을 썼다. 고객 테넌트에서 돌리면 고객 쪽에 작업이 하나 생긴다. 이번에는 매개변수 오류로 실행되지 않았는데, 그 오류를 "라이선스 필요"로 표시하고 있었다.

점검 스크립트는 **보기(Get) 명령만** 쓴다는 원칙을 세트 공통으로 확인받기로 했다.

---

## 7. 오늘 정리

1. **"Cloud Shell에서 된다"에는 조건이 붙는다.** 디바이스 코드가 막힌 테넌트에서는 안 된다.
2. **같은 테넌트에서 두 스크립트를 다 돌리면** 환경 차이와 결함이 바로 갈린다.
3. **목록 조회는 다음 페이지를 끝까지 읽는다.** `$top`만 믿으면 잘린다.
4. **잴 대상이 없어서 나온 0은 정상이 아니다.** 그리고 그 원칙은 스크립트 코드에 있어야 한다.
5. **같은 창에 모듈을 섞지 않는다.** 서비스별로 세션을 나눈다.

남은 것은 판독 기준을 세트끼리 맞추는 일이다. 기본값을 바로 위험으로 볼지, 데이터 없는 0을 어떻게 볼지, 기준표에 칸이 없을 때 어떻게 할지. 이건 스크립트가 아니라 **사람이 정해야 하는** 문제라서, 결정 요청으로 올려 두었다.
