# M365·Azure 실습기 - 남의 스크립트를 내 환경에서 돌려 보는 교차 검증에서 배운 것

## 이 글을 한 줄로

> **"내 환경에서는 잘 돈다"는 검증이 아니다. 다른 사람이 README만 보고 다른 테넌트에서 돌려도 같은 결과가 나와야 끝난다.**

---

## 지난번 이야기 (짧게)

[지난 글]({% post_url 2026-10-28-m365-azure-check-scripts-automation-lessons %})에서는 점검 명령 41개를 스크립트 5개로 묶고, 같은 조 동료 결과와 맞춰 봤다.

이번에는 순서를 바꿨다. **다른 조가 만든 점검 스크립트(41개 항목)를 내 Sandbox에서 직접 실행**하고, 그 조가 제출한 결과와 비교했다. 반대로 그 조는 우리 스크립트를 돌린다. 이것을 교차 검증이라고 부른다.

> 모든 실습은 개인 연습용 환경(M365 개발자 Sandbox)에서 **조회만** 했다. 테넌트 이름과 계정은 글에 적지 않았다.

---

## 1. 실행하기 전부터 막힌다

스크립트를 받아서 실행하기까지 다섯 번 멈췄다. 하나하나는 작은 문제지만, **작성자 PC에서는 한 번도 안 생기는 문제**라는 점이 중요하다.

| 막힌 곳 | 왜 | 해결 |
|---|---|---|
| "디지털 서명이 없습니다" | 메일로 받은 스크립트는 인터넷에서 온 파일로 표시되어 실행 정책에 걸린다 | 이 창에서만 정책 풀기: `Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass` + `Unblock-File` |
| README의 파일 이름이 압축 안 파일 이름과 다름 | 버전을 올리면서 문서만 고침 | 파일 이름을 직접 확인 |
| 실행하자마자 모듈 설치 | 스크립트가 Graph 하위 모듈을 특정 버전으로 자동 설치 | 내 PC가 바뀌므로 **변경 이력에 기록** |
| 로그인 화면에 "이에 대한 액세스 권한이 없습니다" | 스크립트는 디바이스 코드 로그인을 쓰는데, 보안 기본값이 켜진 테넌트는 이를 막는다 | 브라우저 로그인으로 먼저 연결해 두고 실행 |
| 저장 단계에서 오류 | `-Encoding utf8BOM`은 PowerShell 7 전용 | 창을 열고 `pwsh`부터 |

마지막 줄은 이번에 한 번 더 겪었다. 수정본을 받아 돌릴 때 습관처럼 Windows PowerShell 5.1 창에서 실행했더니, 경고 한 줄만 나오고 그대로 진행되어 **모듈 6개를 5.1 쪽에 설치한 뒤** 중단됐다.

> **알게 된 것:** PowerShell 5.1과 7은 모듈 폴더가 따로다. 7에 설치해 둔 모듈이 5.1에는 없어서, 같은 스크립트가 5.1에서는 또 설치를 시작한다. 버전 검사는 **경고가 아니라 멈춤**이어야 한다.

## 2. 가장 큰 발견: 100에서 멈추는 조회

Message center 게시물 중 조치 기한이 임박하거나 지난 것을 세는 항목이 있었다. 우리 Sandbox에서 돌리니 **전체 게시물 100건**이 나왔다. 숫자가 너무 딱 떨어져서 의심했다.

조회 주소에 `?$top=100`이 붙어 있었다. 보통 Graph는 한 페이지가 가득 차면 다음 페이지 주소(`@odata.nextLink`)를 같이 주기 때문에, 그걸 따라가면 나머지를 받을 수 있다. 그런데 이 API는 `$top`을 주면 **다음 페이지 주소를 주지 않았다.**

| 조회 방법 | 전체 게시물 | 기한 임박·경과 |
|---|---|---|
| `$top=100` 그대로 | 100 | 5 |
| `$top` 없이 nextLink를 끝까지 | **495** | **25** |

같은 날 같은 테넌트인데 결과가 5배 다르다. 오류도 경고도 없었다.

> **지난 글의 "빈 화면은 0이 아니다"와 같은 이야기다.** 오류 없이 나온 숫자라도, **끝까지 다 받은 숫자인지** 확인해야 한다. 딱 떨어지는 숫자(100, 500, 999)는 페이지 한도에서 잘린 신호일 수 있다.

우리 조 스크립트에도 같은 유형(첫 페이지만 읽어 9건을 3건으로 센 항목)이 있었기 때문에 바로 알아볼 수 있었다.

---

## 3. 스크립트 결과와 제출한 결과가 다르다

41개 항목을 비교해 보니 판독이 다른 6개 중 3개는 **환경 차이가 아니었다.** 디렉터리 동기화를 쓰지 않는 테넌트에서

- 스크립트는 "동기화 오류 0건 → **정상**"이라고 냈고
- 제출한 결과 파일에는 사람이 "**측정 불가**"로 고쳐 적혀 있었다.

사람의 판단이 맞다. 동기화를 안 쓰면 오류가 생길 일 자체가 없으니 0은 측정값이 아니다. 문제는 **그 판단이 스크립트에 들어가 있지 않았다**는 것이다. 다른 사람이 같은 스크립트를 돌리면 다시 "정상"이 나온다.

> **알게 된 것:** 결과를 손으로 고쳤다면, 그 이유는 스크립트에 돌려 넣어야 한다. 아니면 다음 실행에서 같은 실수가 반복된다.

---

## 4. 수정본을 다시 돌려 보다

지적 8가지를 보내자 같은 날 점심에 수정본이 왔다. 고친 쪽은 "가짜 응답으로만 시험했고 실제 테넌트에서는 아직 못 돌렸다"고 했다. 그래서 우리 실행이 **수정본의 첫 실제 실행**이 됐다.

| 항목 | 수정 전 | 수정 후 |
|---|---|---|
| Message center 게시물 | 100건 | **495건** |
| 동기화 오류 (동기화 미사용) | 정상 | **측정 불가** |
| Connect Health 알림 (동기화 미사용) | 자동 판독 불가 | **측정 불가** |

고친 부분은 모두 의도대로 나왔다. 그런데 새로 넣은 기능 하나는 실제 환경에서 동작하지 않았다.

- 수정본에는 "디바이스 코드가 막히면 자동으로 브라우저 로그인으로 다시 시도"하는 기능이 들어갔다.
- 실제로는 차단 화면이 **브라우저에서만** 뜨고, PowerShell 쪽은 오류를 받지 못한 채 계속 기다렸다.
- 결국 `-BrowserLogin` 옵션을 붙여서 실행했다.

> **알게 된 것:** 가짜 응답 시험은 "응답이 오면 제대로 처리하는가"만 확인한다. **응답이 아예 안 오는 경우**는 실제 환경에서만 드러난다.

## 5. 같은 기준표, 다른 판정

다른 세트(다른 두 조)가 같은 기준표로 낸 결과도 우리 결론과 맞춰 봤다. 41개 중 31개는 결론이 같았고, 10개가 달랐다. 다른 이유는 크게 셋이었다.

1. **같은 문장을 다르게 읽음** — "보고서 미실행 = 위험"에서, 한쪽은 보고서 0건을 그대로 위험으로, 다른 쪽은 "라이선스가 없어서 0인지 안 만들어서 0인지 모른다"며 측정 불가로 봤다.
2. **같은 항목을 다른 화면에서 잼** — 감사 관련 항목을 한쪽은 AI 데이터 보안 화면에서, 다른 쪽은 감사 로그 수집 설정에서 확인했다.
3. **기준표에 칸이 없음** — 개인 계정이 상시 소유자인 경우처럼 정상·주의·위험 어디에도 안 맞는 상황을, 한쪽은 주의로, 다른 쪽은 판독 불가로 남겼다.

세 번째는 우리가 이미 질문으로 올려 둔 항목이었다. 다른 세트에서도 실제로 판단이 갈렸다는 것을 확인한 셈이다.

> **알게 된 것:** 기준표 문장이 짧을수록 사람마다 다르게 읽는다. 판정이 갈린 항목은 누가 맞는지 다투기보다 **기준 문장을 고칠 질문**으로 올리는 게 빠르다.

---

## 6. 오늘 정리

1. **README만으로 실행되는가**가 스크립트 품질의 절반이다. 실행 정책·로그인 방식·PowerShell 버전은 본문 첫 단계에 써야 한다.
2. **딱 떨어지는 숫자는 의심한다.** 페이지 한도에서 잘렸을 수 있다.
3. **사람이 고친 판정은 스크립트로 돌려보낸다.**
4. **가짜 응답 시험 + 실제 실행** 둘 다 해야 한다. 특히 "응답이 안 오는" 상황은 실제로만 보인다.
5. **판정이 갈리면 기준 문장을 고칠 질문으로.**

다음 주에는 다른 세트의 스크립트를 **README만 보고** 돌려 본다. 오늘 우리가 남에게 요구한 것을 이번엔 우리가 지켰는지 확인받는 차례다.
