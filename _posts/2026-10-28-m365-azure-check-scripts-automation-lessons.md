# M365·Azure 실습기 - 점검 명령 41개를 스크립트 5개로 묶고, 동료 결과와 맞춰 본 하루

## 이 글을 한 줄로

> **자동화 스크립트는 "만들었다"가 끝이 아니다. 손으로 확인한 답과 똑같이 나오는지 비교해야 하고, 실행하는 방법까지 정해 줘야 다른 사람도 같은 결과를 얻는다.**

---

## 지난번 이야기 (짧게)

[지난 글]({% post_url 2026-10-26-m365-azure-readonly-checks-41-lessons %})에서는 Microsoft 365·Azure **점검 명령 41개를 하나씩 손으로** 실행했다. 그때 가장 크게 배운 것은 **"빈 화면은 0이 아니다"**였다. 조회가 실패해도 오류 없이 0이 나오는 경우가 많았다.

이번에는 그 41개를 **한 번에 돌릴 수 있는 스크립트**로 만들었다. 실제 운영 환경은 사용자와 구독이 훨씬 많아서 하나씩 손으로 확인할 수가 없기 때문이다.

> 모든 실습은 개인 연습용 환경(M365 개발자 Sandbox)에서 **조회만** 했다. 캡처의 테넌트 이름과 계정은 회색으로 가렸다.

---

## 1. 왜 스크립트가 5개인가

Microsoft 365 안에는 서비스가 여러 개 있고, **서비스마다 들어가는 문(로그인 방식과 명령 묶음)이 다르다.** 그래서 문 하나에 스크립트 하나씩 나눴다.

| 스크립트 | 무엇을 보나 | 비유 | 실행 창 |
|---|---|---|---|
| 01 Graph | 사용자·라이선스·장치·정책 | 인사기록실 | PowerShell 7 |
| 02 Az | Azure 구독·권한·정책 | 건물 관리실 | PowerShell 7 |
| 03 Teams | Teams 회의·채널·앱 설정 | 회의실 규칙판 | PowerShell 7 |
| 04 SPO | SharePoint·OneDrive 공유 설정 | 문서 보관 창고 | **Windows PowerShell 5.1** |
| 05 EXO·IPPS | 감사 기록·DLP·레이블·보존 | CCTV·보안실 | PowerShell 7 |

## 2. 스크립트에 넣은 안전장치

지난번에 손으로 하다가 겪은 함정을 **스크립트가 스스로 피하도록** 만들었다.

**① 조회만 한다.** `Get` 명령과 REST `GET`만 쓴다. 설정을 바꾸는 명령은 아예 넣지 않았다.

**② 한 항목이 실패해도 멈추지 않고, 실패를 "측정 불가"로 적는다.** 실패를 0으로 적으면 안 되기 때문이다.

```powershell
function Invoke-Check {
    param($Id, $Item, $Method, [scriptblock]$Body)
    try { & $Body }
    catch { Add-Row $Id $Item '' '측정 불가' $Method ('실패: ' + $_.Exception.Message) }
}
```

**③ 목록은 끝 페이지까지 읽는다.** Graph는 결과를 여러 쪽으로 나눠 주는데, 첫 쪽만 읽으면 숫자가 적게 나온다. 지난번에 이 실수로 미해결 이슈를 9건이 아니라 3건으로 셌다.

```powershell
function Get-GraphAll {
    param([string]$Uri)
    $out = @(); $next = $Uri
    while ($next) { $r = Invoke-MgGraphRequest -Method GET -Uri $next; $out += $r.value; $next = $r.'@odata.nextLink' }
    return $out
}
```

**④ "오류 없는 실패"를 잡는다.** `Invoke-AzRestMethod`는 권한이 없어도(403) 오류를 내지 않는다. 그래서 상태 코드부터 확인한다.

**⑤ 없는 속성을 빈칸으로 읽지 않는다.** 모듈 버전에 따라 속성이 없으면 `Select-Object`가 조용히 빈칸을 만든다. 실제 속성 목록과 먼저 대조한다.

**⑥ 고장 난 모듈 버전이면 시작도 안 한다.** SharePoint 모듈 최신판(16.0.27709)은 로그인 부품이 빠져 있어서 접속이 안 된다. 그래서 정상 버전이 아니면 스크립트가 바로 멈추게 했다.

```powershell
if ($PSVersionTable.PSVersion.Major -ne 5) { throw "Windows PowerShell 5.1에서 실행하세요" }
$loaded = @(Get-Module Microsoft.Online.SharePoint.PowerShell)
if ($loaded.Count -ne 1 -or "$($loaded[0].Version)" -ne '16.0.27612.12000') { throw "SPO 모듈 버전 불일치" }
```

**⑦ 결과는 모두 같은 7칸 표(CSV)로 저장한다.** 측정 ID / 항목 / 측정값 / 판독 / 실행 일시 / 조회 방법 / 비고. 여러 사람의 결과를 합칠 수 있게 칸 이름과 순서를 맞췄다.

## 3. 돌려 보니 생긴 일 5가지

스크립트를 만들고 실제로 돌리자 **월요일에 손으로 한 결과와 41개 모두 같은 값**이 나왔다. 다만 거기까지 가는 동안 다섯 번 넘어졌다. 세 번은 실행 방법 문제였고, 두 번은 내 실수였다.

### 넘어짐 1. 스크립트를 붙여 넣었더니 안전장치가 무력화됐다

SharePoint 스크립트를 실행했는데 10개 항목이 전부 실패했다. 알고 보니 **PowerShell 7 창에 스크립트 내용을 붙여 넣어서** 실행한 것이었다.

![PowerShell 7 창에 붙여 넣은 흔적과 Get-SPOTenant를 찾지 못하는 오류](/assets/images/2026-10-28-scripts/01_ps7_paste_fail.png)

스크립트 맨 앞에는 "5.1이 아니면 멈춤" 검사가 있다. 그런데 **파일로 실행할 때만** 멈춘다.

| 실행 방법 | 검사에 걸리면 |
|---|---|
| `.\파일이름.ps1` | 스크립트 전체가 멈춘다 |
| 내용 붙여 넣기 | 그 줄만 빨간 오류를 찍고 **다음 줄이 계속 실행된다** |

비유하면 파일 실행은 "문이 잠겨 있으면 집에 못 들어감"이고, 붙여 넣기는 "문에 '잠김' 경고만 붙여 놓고 창문으로 계속 들어감"이다.

> **교훈:** 안전장치는 실행 방법까지 정해 줘야 작동한다. 사용법 메모에 "붙여 넣지 말고 `.\파일`로 실행"을 첫 줄로 적었다.

### 넘어짐 2. 명령 두 줄이 한 줄로 붙었다

5.1 창을 제대로 열고 모듈 버전도 확인했는데, 마지막에 명령 두 개가 이어 붙었다.

![두 명령이 붙어서 테넌트 이름 뒤에 Set-ExecutionPolicy가 이어진 화면](/assets/images/2026-10-28-scripts/02_ps51_glued_command.png)

PowerShell은 테넌트 이름을 `<테넌트>Set-ExecutionPolicy`로 읽었고, `-Scope`는 스크립트에 없는 옵션이라 시작 전에 멈췄다. 다행히 **아무것도 실행되지 않았다.** 한 줄씩 입력해서 해결했다.

### 넘어짐 3. 날짜의 `+`가 공백으로 바뀌었다 (내 실수)

Azure Policy 조회(X-81)가 이런 오류를 냈다.

```
The value '2026-10-26T08:57:36.7113353 09:00' was provided for from; a valid datetime value must be provided.
```

`09:00` 앞에 원래 `+`가 있었다. 한국 시간(`+09:00`)으로 날짜를 넘겼는데, 주소(URL)에 실리면서 **`+`가 공백으로 바뀌어** Azure가 날짜를 못 읽었다. URL에서 `+`는 공백을 뜻하기 때문이다.

```powershell
# 수정 전: -From (Get-Date).AddDays(-2)                     → ...T08:57:36+09:00
# 수정 후: -From (Get-Date).ToUniversalTime().AddDays(-2)   → ...T23:57:36Z
```

UTC로 바꾸면 `+` 대신 `Z`가 붙어서 깨질 일이 없다.

![수정 후 Az 스크립트 실행 결과, 4개 항목 모두 조회됨](/assets/images/2026-10-28-scripts/03_az_v3_success.png)

### 넘어짐 4. 필요 없는 옵션을 붙였다가 거절당했다 (내 실수)

SharePoint 데이터 접근 보고서(X-61, X-63)를 조회할 때 `-ReportType Snapshot -Workload SharePoint`를 붙였다. 그러자 "이 보고서 종류에는 그 옵션을 쓸 수 없다"며 거절당했다.

![SharePoint 스크립트 1차 실행. 7개는 조회됐고 X-61·63·62는 측정 불가](/assets/images/2026-10-28-scripts/04_spo_v1_partial.png)

MS 문서를 다시 보니 두 옵션은 **선택 사항**이었고, 예시도 `-ReportEntity`만 썼다. 옵션을 빼자 정상 조회됐다.

> **교훈:** "옵션을 더 붙이면 더 정확하겠지"는 착각이다. 문서의 예시 형태부터 맞춘다.

### 넘어짐 5. 여러 모듈 버전을 한 번에 물어봤다가 오류

환경 정보를 정리하려고 모듈 버전을 한 번에 조회했더니 오류가 났다.

![Get-InstalledModule에 이름 여러 개와 -AllVersions를 함께 써서 난 오류](/assets/images/2026-10-28-scripts/05_allversions_error.png)

`-AllVersions`는 **모듈 이름을 하나만 줄 때만** 쓸 수 있다. 이름마다 따로 묻도록 바꿨다.

```powershell
'Microsoft.Graph','Az','MicrosoftTeams','ExchangeOnlineManagement','Microsoft.Online.SharePoint.PowerShell' |
  ForEach-Object { Get-InstalledModule $_ -AllVersions -ErrorAction SilentlyContinue } |
  Format-Table Name, Version -AutoSize
```

![모듈별 설치 버전. SharePoint 모듈은 두 버전이 함께 설치되어 있다](/assets/images/2026-10-28-scripts/06_module_versions.png)

## 4. 자동화하다가 저지른 판단 실수

스크립트를 만들면서 "제가 임의로 정한 기준으로 판독하면 안 되겠다"고 생각했다. 그래서 몇몇 항목(잔여 라이선스 비율, 저장소 사용률 등)의 **자동 판독을 빼 버렸다.**

그런데 나중에 기준표를 다시 읽어 보니, 그 수치들(잔여 10% 이상이면 위험, 5~10%면 주의 등)은 **원래 기준표에 적혀 있던 기준**이었다. 내가 만든 숫자가 아니었다.

> **교훈:** "임의로 판단하지 말자"는 원칙은 맞다. 하지만 원칙을 지키려면 **그 기준이 어디서 왔는지부터 확인**해야 한다. 확인 없이 빼는 것도 또 다른 임의 판단이다.

## 5. 동료의 결과와 맞춰 보기

같은 41개 항목을 동료도 따로 측정했다. 둘을 나란히 놓으니 이렇게 나왔다.

| 비교 결과 | 건수 |
|---|---|
| 값도 판독도 같음 | 13 |
| 값은 같은데 판독이 다르거나 비어 있음 | 22 |
| 값 자체가 다름 | 6 |

### 값이 다른 이유는 "환경이 달라서"만이 아니었다

두 사람은 서로 다른 Sandbox를 썼으니 숫자가 다른 게 당연해 보인다. 그런데 하나씩 보니 **다른 이유**가 더 많았다.

| 이유 | 실제 예 |
|---|---|
| **측정 방법이 다름** | 직접 할당 라이선스를 세는 식이 달라서, 같은 테넌트에서도 22명과 23명이 나온다 |
| **잰 대상이 다름** | 한 사람은 "외부 공유 수준"을, 다른 사람은 "기본 링크 유형"을 적었다. 이름은 비슷해도 다른 설정이다 |
| **잰 시점이 다름** | 미해결 서비스 이슈가 이틀 사이 9건에서 10건이 됐다 |
| **적는 방식이 다름** | 같은 "없음"을 `Null`, `0`, 공란, "정책없음"으로 적었다 |
| **접속 순서·권한이 다름** | 접속 순서에 따라 감사 설정이 항상 False로 보이고, 청구 권한이 없으면 청구 계정이 0으로 보인다 |
| **모듈 버전이 다름** | 버전에 따라 속성이 있기도 하고 없기도 하다 |

> **교훈:** 값이 다를 때 "환경 탓"으로 끝내면 안 된다. **같은 스크립트를 양쪽에서 돌려 봐야** 진짜 환경 차이인지 알 수 있다.

### 판독이 갈린 이유: 같은 기준, 다른 해석

판독이 다른 22건은 대부분 기준표의 이 문장 때문이었다.

> **"결정 근거 없이 MS 기본값 유지 = 위험"**

연습 환경은 기본값 그대로이고 결정 근거도 없으니 문장대로라면 위험이다. 하지만 실제 회사라면 "기본값을 쓰기로 결정한 근거"가 있을 수도 있다. 동료는 "위험"으로, 나는 "고객 기준을 봐야 한다"며 "보류"로 적었다.

## 6. 결론을 하나로 맞추는 법: 항목 말고 원칙을 합의하기

41개를 하나씩 맞추면 끝이 안 난다. 그래서 **판정 원칙 5개**를 먼저 제안했다.

1. **측정은 하나로 통일** — 같은 스크립트로 잰 결과 하나를 기준으로 하고, 다른 결과는 교차 확인용으로 둔다.
2. **기준표 문구 그대로** — 수치나 조건이 적힌 항목은 기준표대로만 판독한다.
3. **기본값 항목은 두 줄로** — "연습 환경: 위험 조건 해당 / 실제 환경: 고객 기준 확인 필요". 두 사람 의견을 모두 담는다.
4. **0은 두 가지로 구분** — 실제로 조회한 0은 "정상(대상 없음)", 데이터가 아예 없는 0은 "측정 불가".
5. **기준표가 답을 못 주면 그것도 결론** — "판독 불가(사유)"로 확정하고 질문으로 올린다.

원칙이 정해지자 41개 결론이 **자동으로 한 줄씩** 나왔고, 동료도 바로 동의했다.

| 결론 | 건수 |
|---|---|
| 위험 | 9 |
| 기본값 유지(위험 조건) · 실제 환경 기준 확인 | 13 |
| 주의 | 3 |
| 정상 (대상 없음 포함) | 3 |
| 측정 불가 (연습 환경에 라이선스·장치·데이터 없음) | 10 |
| 판독 불가 (기준표 공백·예외 목록 없음) | 2 |
| 실제 환경 기준과 대조 필요 | 1 |

> **교훈:** 의견이 갈릴 때는 각 항목을 두고 다투지 말고, **판단하는 규칙**을 먼저 맞춘다. 규칙이 같으면 결론은 저절로 같아진다.

## 7. 다른 팀에 넘길 때: 질문이 안 나오게 한 묶음으로

결론을 다른 조에 메일로 넘기면서 **압축 파일 하나**에 전부 담았다.

```
00_먼저읽기.md          볼 순서, 판정 원칙, 실행 환경, 재실행 주의 5가지
01_결론/                결론 41개 (엑셀 + 표준 CSV)
02_스크립트/            스크립트 5개 + 사용법 메모
03_실측결과/            스크립트를 실제로 돌린 원본 결과
04_검증표/              항목별 검증 상태·수정안
05_질문_미확인/         아직 답을 모르는 것
06_캡처/                근거 화면
```

넣으면서 지킨 것:
- **결론만이 아니라 근거(원본 결과·캡처)까지** 넣는다.
- **실행 환경(모듈 버전, 라이선스, 데이터 상태)을 적는다.** 같은 스크립트라도 환경이 다르면 결과가 다르기 때문이다.
- **내가 겪은 실패를 "재실행 주의"로 적는다.** 붙여 넣기 금지, 모듈 버전, 접속 순서 같은 것들이다.
- **개인 간 판독 차이는 빼고 팀 결론만** 넣는다. 받는 쪽은 "그래서 답이 뭔지"가 필요하다.
- **테넌트 이름·계정은 가린다.**

정리하다가 질문 번호를 잘못 적은 것도 하나 발견해서 바로잡았다. 묶음을 만드는 과정이 마지막 검토가 됐다.

## 오늘의 교훈 정리

1. **자동화의 첫 실행은 반드시 손으로 확인한 답과 비교한다.** 비교하다가 내 실수 2개를 찾았다.
2. **안전장치는 실행 방법까지 정해야 작동한다.** 스크립트는 붙여 넣지 말고 파일로 실행한다.
3. **날짜·옵션·매개변수는 문서 예시 형태를 따른다.** 더 붙인다고 더 정확해지지 않는다.
4. **"임의 판단 금지"를 지키려면 기준의 출처부터 확인한다.**
5. **값이 다를 때 "환경 탓"으로 끝내지 않는다.** 방법·대상·시점·표기·권한·버전부터 의심한다.
6. **의견이 갈리면 항목이 아니라 원칙을 합의한다.**
7. **넘길 때는 결론 + 근거 + 환경 + 겪은 실패를 한 묶음으로 준다.**

다음에는 다른 조의 스크립트를 사용법 메모만 보고 돌려 보는 **교차 실행**을 한다. 내 메모만으로 다른 사람이 같은 결과를 얻을 수 있는지가 진짜 시험이다.
